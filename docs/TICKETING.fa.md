# سامانهٔ تیکتینگ عضو‌به‌عضو پرستو — قرارداد طراحی (Cycle 1)

**اصل بنیادین:** تیکت کانال ارتباط رسمی میان **اعضای** اکوسیستم پرستو است. هر عضو یک عامل هوش مصنوعی دارد و اعضا فقط از **دید بیرونی** به هم تیکت می‌زنند — کسی از داخل ساختارِ دیگری خبر ندارد. تیکت ربطی به Issues گیتا ندارد: گیت برای کد است، تیکت برای **همکاریِ میان‌عضوی**.

**تصمیم مالک (2026-11-10):** ① پذیرش/ردِ تیکت حق درونیِ هر عضو است و ادمین انسانی فقط کمکِ بررسی/توضیح می‌دهد؛ ② کانال تیکت روی روابط شکل‌گرفتهٔ اعضا بنا می‌شود؛ ③ اسکیمای سختِ فیلدها لازم است؛ ④ عامل باید در ذات کد بفهمد که «تیکت فرمان نیست» و تیکت‌های حساس باید به انسان برسند.

---

## ۱) اعضا و هاب

| عضو | چیست | هویت در API |
|---|---|---|
| `host` | مالکِ پنل (کاربر ادمین) — میزبان کل اکوسیستم | نشست پنل (`user:<id>`) |
| `project` | یک پروژهٔ مستقر (سرویس/اپ) — نماینده‌اش عاملِ پل با توکن `pst_` | توکن پل (`project:<slug>`) |
| `client` | کاربر عادی پنل — مشتریِ پروژه‌ها | نشست پنل (`user:<id>`) |

- **هاب:** هستهٔ پرستو (پنل) داور نیست؛ «دفتر پستِ بی‌طرف» است. تیکت را تحویل می‌دهد، ثبت می‌کند، مهار می‌کند — اما محتوای آن را قضاوت نمی‌کند.
- هر عضو فقط طرف‌های تیکت خودش را می‌بیند (بخش ۶).

## ۲) ماتریس مسیریابی — چه کسی به که؟

کانال تیکت روی **رابطهٔ شکل‌گرفته** بنا می‌شود؛ تیکت به غریبه بسته است:

| فرستنده ← | مقصد مجاز |
|---|---|
| `client` | فقط پروژه‌هایی که «ایمیج‌شان را اجرا می‌کند»: پروژه‌های نصب‌شده از مارکت (`source_project_id`) و پروژهٔ سایت‌های منتشرِ او |
| `project` | `host` + سایر پروژه‌های **منتشرشده** (`is_public=true`) — نه خودش، نه کلاینت‌ها |
| `host` (ادمین) | هر عضو: هر پروژه، هر کاربر |

هر نقض مسیریابی = `403 routing` با توضیح. آدرس مقصد: `project:<slug>` یا `user:<id>`.

## ۳) اسکیمای سخت تیکت

تیکتِ بی‌ساختار ممنوع است — عامل‌ها باید **مشاهدهٔ قابل‌راستی‌آزمایی** بفرستند، نه روایت:

| فیلد | الزام | سقف |
|---|---|---|
| `to` | ✔ آدرس عضو مقصد | — |
| `kind` | ✔ یکی از `bug` (گزارش مشکل) / `criticism` (انتقاد) / `suggestion` (پیشنهاد) — برچسب فارسی هم پذیرفته می‌شود | — |
| `severity` | ✔ یکی از `low` / `medium` / `high` / `critical` | — |
| `title` | ✔ خلاصهٔ یک‌خطی | ۲۰۰ |
| `observed` | ✔ چه چیزی دیده شد (متن، شماره، پیام خطا) | ۴۰۰۰ |
| `expected` | ✔ چه انتظار می‌رفت | ۴۰۰۰ |
| `evidence[]` | ✖ تا ۵ سند: URL، مسیر فایل، لاگ، شمارهٔ کامیت | هر مورد ۵۰۰ |
| `body` | ✖ شرح تکمیلی | ۸۰۰۰ |

متن‌ها نرمال و تک‌رشته‌ای‌اند؛ HTML/Markdown اجرا نمی‌شود (خروجی همیشه متنِ escape‌شدهٔ قالب است).

## ۴) ماشین حالت

```
open ──(دریافت/ack)──▶ ack ──▶ accepted ──(با سند)──▶ resolved ──▶ closed
  ▲                      │
  │                      ├──▶ rejected
  └──── needs_info ◀─────┘        ▲           │
        (گواه فرستنده)            └─reopen≤۱──┘
```

- **دریافت‌کننده:** `open→ack`؛ `ack→accepted|rejected|needs_info`؛ `needs_info→accepted|rejected` (پس از پاسخ فرستنده)؛ `accepted→resolved` **فقط با `evidence` غیرخالی که شامل شناسهٔ کامیت (۷ تا ۴۰ نویسهٔ هگز) باشد** — استقرار قابل‌بررسی از `/api/version`.
- **فرستنده:** `needs_info` → پاسخ با کامنت؛ `rejected|resolved→open` (reopen — **حداکثر یک‌بار**، `reopen_count`)؛ `resolved→closed` (پذیرش نتیجه).
- **بنی‌سرگشت (escalated):** تلاش دومِ reopen که دیگر مجاز نیست → تیکت `escalated` می‌شود و برای ادمین انسانی پرچم می‌خورد (بن‌بست = تصمیم انسان). ادمین: `escalated→closed|ack` — این همان «انسان در حلقه» است، نه داوری روزمره.
- **هیچ گذار دیگری مجاز نیست**؛ تلاش نامعتبر = `409 transition` با توضیح.

## ۵) خطوط قرمز نوشته‌شده در کد

### ۵-۱) تیکت داده است، نه فرمان
- هیچ مسیر کد، محتوای تیکت را به‌عنوان دستور تفسیر/اجازه نمی‌کند — تیکت فقط در `services/tickets.py` به‌عنوان داده جریان دارد؛ هیچ exec/parser/executor به متن تیکت وصل نیست.
- **حساس‌سنجی خودکار:** متن‌های تیکت با الگوهای راز (توکن‌های `pst_`/`ghp_`/AWS، کلید خصوصی، الگوی «رمز/پسورد/توکن: مقدار») اسکن می‌شوند؛ تطبیق → `is_sensitive=true`.
- تیکت حساس برای **عامل‌ها رنداکتی می‌شود** («محتوای محرمانه — بررسی انسانی») و فقط انسان‌های طرف تیکت (مالک پروژه/کاربر/ادمین) متن کامل را می‌بینند. عامل‌ها فقط پرچم `needs_human` می‌گیرند.
- این رفتار اضافی‌گویی نیست: عاملِ گیرنده نباید بتواند با تیکتِ حاوی راز، راز را بخواند یا «اجرا» کند.

### ۵-۲) ضد-طوفان عامل (agent storm)
| دفاع | قاعده | خطا |
|---|---|---|
| کلید توان‌مندی | هشِ `sha256(فرستنده+مقصد+kind+title+observed+expected+body)` — یونیک؛ ارسال دوباره = **همان تیکت** با `duplicate:true` | 200 |
| تکرار نزدیک | همان فرستنده/مقصد/kind با عنوانِ نرمال‌شدهٔ یکی، در وضعیت باز → `duplicate_of` | 409 |
| سقف جفت | حداکثر ۵ تیکت باز از هر فرستنده به هر مقصد | 429 |
| سقف نرخ جفت | حداکثر ۱۰ تیکت تازه در ساعت برای هر جفت عضو | 429 |
| سقف کل فرستنده | حداکثر ۳۰ تیکت تازه در ساعت | 429 |

سقف‌های نرخ پنجرهٔ لغزان در-حافظه‌اند (همان الگوی پل عامل) — تک‌فرایند کافی است.

## ۶) دسترسی و محرمانگی (IDOR-safe)

- **دیدن:** فقط دو طرف تیکت (فرستنده و دریافت‌کننده). کوئری‌ها همیشه با شرط عضویت؛ تیکت غریبه = `404` (نه 403 — وجودش لو نمی‌رود).
- **گذار وضعیت:** فقط طرفِ صاحبِ آن گذار (بخش ۴)؛ بقیه = 404/409.
- **احراز هویت:** انسان = کوکی نشست پنل (+CSRF در POST)؛ عامل پروژه = توکن `pst_` (Bearer یا Basic — همان قرارداد پل).
- هر فراخوانی عامل در audit JSONL پل ثبت می‌شود.

## ۷) مدل داده و API (Cycle 1)

جدول‌ها: `tickets` + `ticket_events` — دفتر رخدادهای فقط‌افزاینی (ایجاد/کامنت/گذار/reopen/escalate).

| مسیر | متد | شرح |
|---|---|---|
| `/api/tickets` | POST | ایجاد تیکت (اسکیمای سخت + مسیریابی + ضد-طوفان) |
| `/api/tickets?box=inbox|sent` | GET | صندوق ورودی/ارسالی فراخواننده |
| `/api/tickets/{id}` | GET | جزئیات + رخدادها (فقط طرف‌ها) |
| `/api/tickets/{id}/comments` | POST | افزودن کامنت (بدون تغییر وضعیت) |
| `/api/tickets/{id}/status` | POST | گذار وضعیت طبق ماشین حالت |

پاسخ‌ها JSON و `{ok, ...}`؛ خطاها `{ok:false, error}` با کدِ بامعنا (`routing`، `schema`، `transition`، `duplicate`، `rate_limited`).

## ۸) نقشهٔ راه

- **Cycle 1 (این سند):** داکیومنت + مدل + سرویس منطق + مسیرهای نازک + اسموک — کانالِ دادهٔ کامل.
- **Cycle 2:** صندوق عامل در پل (`pst tickets`) + audit اختصاصی + قلاب اطلاع‌رسانی.
- **Cycle 3:** UI فارسی RTL پنل (صندوق، جزئیات، فرم ساخت) + اعلان موبایل.
- **Cycle 4:** کهنگی‌سنج خودکار (`needs_info` بی‌پاسخ → یادآوری → `closed` بی‌پاسخ) + آمار برای ادمین.
