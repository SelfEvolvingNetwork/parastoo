# الگوی ارتباط سرویس‌ها (Service Communications) — قرارداد v0.4.6

## تصمیم در یک خط

پروژه‌ها با **API استاندارد** قابل دسترس‌اند — چه از وب جهانی، چه از پروژه‌های دیگرِ
روی همان سرور. تنها درِ مشترک، **URL عمومی** است: `https://<slug>.apps.<دامنه>`.
فراخوانندهٔ وب و فراخوانندهٔ همسایه دقیقاً یک رفتار، یک احراز هویت و یک سطح دسترسی
می‌بینند؛ هیچ مسیر ویژهٔ «داخلی» وجود ندارد که جداگانه امنش کنیم.

*(تصمیم مالک — 2026-11-07؛ پشتوانهٔ میدانی: آزمون hairpin بین-پروژه‌ای v0.4.6.)*

## سطح A — ارتباط درون-پروژه‌ای (کانتینر به کانتینر همان پروژه)

هر پروژه شبکهٔ خصوصی خودش را دارد (`parastoo-proj-<id>`) و هر سرویس با **نام کوتاه
خودش به‌عنوان alias شبکه** ثبت می‌شود. پس فراخوانی با «نام سرویس + پورت مانیفست»:

```yaml
# parastoo.yml
services:
  web:
    build: .
    port: 80
    public: true
    env: [DATABASE_URL=postgres://db:5432/app, CACHE_URL=redis://cache:6379/0]
  db:
    image: postgres:16-alpine
    volume: dbdata:/var/lib/postgresql/data
  cache:
    image: redis:7-alpine
```

قواعد:

1. **نام مقصد = نام سرویس در مانیفست** (`db`، `cache`) — نه نام کانتینر کامل
   (`parastoo-p<id>-db` هرگز resolve نمی‌شود؛ درس میدانی v0.4.1).
2. **پورت مقصد = پورت مانیفست سرویس مقصد** — نه ۳۰۰۰ پیش‌فرض، نه پورت عمومی.
   (میدان v0.4.6: فراخوانی `web:3000` برای سرویسی با `port: 80` → Connection refused.)
3. ترتیب راه‌اندازی با پرستو است (غیرعمومی‌ها اول، سرویس عمومی آخر — جایگزین
   `depends_on`)؛ اپ باید آماده‌شدن مقصد را با تلاش دوباره بپذیرد (سیاست
   restart پرستو `unless-stopped` است).
4. سرویس‌های غیرعمومی از بیرون و از پروژه‌های دیگر **هیچ‌وقت** قابل تماس نیستند —
   به‌ساختار (آزمون زندهٔ v0.4.2: سرویس `db` پروژهٔ ۲ از پروژهٔ همسایه NOT-RESOLVED).

تأخیر میدانی این مسیر: **~۲ میلی‌ثانیه** (بریج خصوصی؛ اندازه‌گیری v0.4.6: 200 در 1.9ms).

## سطح B — ارتباط بین-پروژه‌ای و از وب جهانی (درِ واحد)

مسیر: فراخوانی‌کننده → DNS/IP → ترافیک (TLS وایلدکارد `*.apps.<دامنه>`) →
کانتینر **سرویس عمومیِ** پروژهٔ مقصد. برای فراخوانندهٔ روی همان سرور این یک
hairpin داخلی است — بستهٔ شبکه از سرور بیرون نمی‌رود.

قواعد قرارداد:

1. **احراز هویت انتها-به-انتها با اپ است** — «دسترس‌پذیری شبکه ≠ اعتماد». چون
   همین در به وب جهانی هم باز است، هر API منتشرشده باید خودش توکن/API-key
   را اعتبارسنجی کند؛ پلتفرم فقط حمل می‌کند (TLS + مسیر پایدار).
2. **پورت داخلی از دید فراخوانندهٔ بین-پروژه‌ای بی‌معناست** — ترافیک خودش به
   پورت مانیفستِ سرویس عمومی می‌رود. URL کامل بدهید، نه host:port دست‌ساز.
3. **پروژهٔ منتشرنشده نامرئی است** — نه از وب، نه از همسایه (انتشار = تصمیم
   مالک + گارد کیف پول).
4. سرویس‌های غیرعمومیِ مقصد (db/cache) از این مسیر هم دیده نمی‌شوند؛ فقط همان
   چیزی که اپِ مقصد روی سرویس عمومی‌اش ارائه کند.

تأخیر میدانی: **~۰٫۲ ثانیه** برای اتصال تازه (DNS 56ms + TLS 56ms + رفت‌وبرگشت)؛
با اتصالِ نگه‌داشته‌شده (keep-alive) به‌ازای هر فراخوانی به‌مراتب کمتر.

## DNS خوداتکا (v0.4.6) — پین نام‌های پلتفرم در /etc/hosts

**مسئله:** رزولوشن نام‌های `*.apps.<دامنه>` از داخل کانتینرها تا امروز از DNS
بالادست می‌گذشت (~۵۶ms؛ و ریسک SERVFAIL شناخته‌شدهٔ دامنه‌های .ir از ایران —
درس v0.3.35). فراخوانی شرق-غرب نباید به رزولور بیرونی وابسته بماند.

**آزمون میدانی که طراحی را تعیین کرد (v0.4.6):** پیشنهاد طبیعی
`--dns [نیم‌سرور خودمان، بالادست]` **باطل شد**: forwarder داکر روی شبکهٔ
user-defined با پاس **REFUSED** نیم‌سرورِ اول (PowerDNS فقط authoritative است)
سرِ اول می‌ماند و به سراغ رزولور دوم نمی‌رود — نتیجه: `google.com` و `pypi.org`
با `EAI_AGAIN` بعد از ۵ ثانیه شکست خوردند (خروجی egress کانتینرها می‌شکست).

**راه‌حل:** هنگام هر استقرار، نام‌های پلتفرم در `/etc/hosts` کانتینرهای پروژه
**پین می‌شوند** (docker `hosts`/ExtraHosts):

- نام‌های زیرساخت: `panel.` و `git.` و دامنهٔ پایه و `www.`
- همهٔ سایت‌های منتشرشدهٔ همهٔ پروژه‌ها (`<slug>.apps.<دامنه>` و دامنه‌های
  اختصاصیِ متصل‌شده) — منبع حقیقت: جدول `sites`.
- IP هدف: `PARASTOO_DNS_BIND_IP` از .env هاست (نصب‌کننده محلی‌بودنش را گارد
  می‌کند — درس v0.3.25)؛ فال‌بک `PARASTOO_PUBLIC_IP`؛ غیبت هر دو = قابلیت خاموش.
- ترافیک 80/443 را روی همهٔ اینترفیس‌ها پابلیش می‌کند، پس همین IP مسیر
  hairpin کانتینر→ترافیک را هم باز می‌کند (connect میدانی: 0.2ms).

**ویژگی‌های ایمن این پین:**

- زنجیرهٔ رزولوشن بیرونی دست‌نخورده می‌ماند (egress مثل قبل) — فقط نام‌های
  خودمان از بالادست جدا می‌شوند.
- ورودی کهنه بی‌ضرر است: نام حذف‌شده → 404 ترافیک (همان رفتار مسیر DNS).
- نام منتشرشدهٔ *بعد از* این استقرار تا deploy بعدی از DNS بالادست می‌آید —
  پین **شتاب‌دهنده** است، نه پیش‌شرط درستی.
- پین با هر پوش/بیلد/انتشار (هر `deploy_project`) تازه می‌شود.

## مرزها و ایده‌های ثبت‌شده (صادقانه)

- فراخوانی بین-پروژه‌ای با حجم بالا از مسیر عمومی، هزینهٔ TLS/hairpin دارد.
  اگر روزی workload واقعی طلب کرد: (۱) ریکورسور داخلی با فوروارد داینامیک
  زون‌ها، یا (۲) «شبکهٔ پیوند» opt-in با اتصال فقط سرویس عمومیِ مقصد
  (الگوی least-privilege — تحلیل 2026-11-07). فعلاً هیچ‌کدام ساخته نشد:
  سادگی می‌ارزد.
- نسخه‌بندی/CORS/سقف نرخِ API خودِ اپ، کار اپ است؛ پلتفرم فقط قراردادِ
  «URL پایدار + TLS + درِ واحد» را تضمین می‌کند.

## چک‌های خودکار

- `e2e_live.py` با `PARASTOO_BRIDGE_TOKEN` + `PARASTOO_CROSS_TARGET`:
  چک `bridge-cross` (فراخوانی API پروژهٔ دیگر از داخل کانتینر) و
  `bridge-hosts` (بودن پین در /etc/hosts) — بدون این env ها SKIP تمیز.
- اسموک آفلاین: سازندهٔ نقشهٔ پین (`pin_host_entries`) — نام‌های زیرساخت + سایت‌ها
  + خاموشی قابلیت وقتی IP غایب است.
