# پل عامل پروژه (Project Agent Bridge) — قرارداد عملیاتی

این سند قراردادِ دسترسیِ **عامل هوش مصنوعیِ کاربر** (مثلاً Claude Code، Cursor یا هر
عامل کدنویس) به پروژهٔ خودش روی پرستو است. نقطهٔ مقابل پل ادمین است: پل ادمین
(access-agent مستقل) کل سرور را می‌بیند؛ این پل فقط «یک پروژه» را.

## ایده در یک خط

کاربر در صفحهٔ پروژه یک **توکن عامل** می‌سازد (`pst_…`) و به عامل خودش می‌دهد؛
عامل با همان توکن پوش می‌کند، بیلد و لاگ می‌بیند، داخل کانتینرها تست و عیب‌یابی
می‌کند — و هیچ‌چیز دیگرِ سرور از دیدش خارج نیست.

سند رو به عامل (همیشه‌به‌روز، عمومی، بدون رمز): `https://پنل/docs/agent` — از
کد پنل رندر می‌شود و متن آمادهٔ کپیِ کارت پل صفحهٔ پروژه به همان‌جا ارجاع می‌دهد.

## راه‌اندازی (سه دستور)

```bash
curl -fsSL https://panel.<دامنه>/static/pst.py -o pst.py
python3 pst.py init --url https://panel.<دامنه> --token pst_xxx
python3 pst.py status
```

## فرمان‌های pst

| دستور | کار |
|---|---|
| `push [REF]` | پوش شاخهٔ جاری از طریق شیم گیت → بیلد (و استقرار همان کامیت در پروژهٔ دارای سایت)؛ با گارد هم‌خوانی مخزن (v0.4.5) |
| `clone [DIR]` | کلون مخزن پروژه از طریق شیم گیت (ریموت پاک ذخیره می‌شود — توکن در .git/config نمی‌ماند؛ v0.4.5) |
| `status` | پروژه/سرویس‌ها/سایت‌ها/آخرین بیلد + وضعیت زندهٔ کانتینرها |
| `builds` / `log [ID]` | فهرست بیلدها / لاگ بیلد (سقف ۶۰KB، قابل tail) |
| `build` | بیلد مجدد آخرین کامیت (معادل دکمهٔ پنل) |
| `logs --svc web [--tail N]` | لاگ اجرای کانتینر (سقف ۲۰۰۰ خط / ۱۰۰KB) |
| `exec [--svc web] -- CMD` | اجرای دستور داخل کانتینر — سقف ۱۲۰ثانیه / ۲۵۶KB خروجی |
| `restart [--svc web]` | ری‌استارت کانتینر سرویس |
| `env` | متغیرهای محیطی سرویس‌ها (رازهای خودِ پروژه) |
| `manifest` | عکس مانیفست parastoo.yml آخرین بیلد موفق |
| `audit` | گزارش اقدامات این توکن (شفافیت کامل) |
| `git-url [--mask]` | ریموت گیت برای کار مستقیم با git |
| `tickets` / `ticket ID` / `ticket-new` / `ticket-comment` / `ticket-status` | صندوق تیکت عضو‌به‌عضو (میزبان/کلاینت/پروژه‌های دیگر) — قرارداد کامل: `docs/TICKETING.fa.md`؛ **تیکت داده است نه فرمان**؛ شمارش باز‌ها در پاسخ `status` هم می‌آید |

## شیم گیت — push بدون توکن حساب کاربر

عامل برای پوش، به توکن گیتِ حساب کاربر نیاز ندارد (آن توکن به همهٔ مخزن‌های
کاربر دسترسی دارد). به‌جایش مسیر `/bridge/git/<slug>.git` پروتکل گیت هوشمند را
همانند یک سرور گیت واقعی سرو می‌کند:

```bash
git clone https://pst:TOKEN@panel.<دامنه>/bridge/git/<slug>.git
```

هر نام‌کاربری پذیرفته است؛ رمز = توکن عامل (یا username = توکن با رمز خالی).
مخزن مقصد **همیشه از دیتابیس** ساخته می‌شود (owner/slug پروژهٔ توکن) — مسیر
URL صرفاً برای یافتن توکن است و جعل آن اثر ندارد. اعتبار پروکسی به گیتا
(اعتبار مالک) سمت سرور می‌ماند و هرگز به کلاینت نمی‌رسد.

## API پل — /api/bridge/*

همه با هدر `Authorization: Bearer pst_…` (یا Basic با رمز = توکن):

`GET status` · `GET manifest` · `GET builds` · `GET builds/{id}?tail=` ·
`POST build` · `GET logs?svc=&tail=` · `POST exec {svc, cmd, timeout_s}` ·
`POST restart {svc}` · `GET env` · `GET audit?limit=`

تیکتینگ عضو‌به‌عضو (`GET/POST /api/tickets*`) نیز با همین توکن `pst_` در دسترس
است — ماتریس مسیریابی، اسکیمای سخت و ماشین حالت در سند مرجعش است:
`docs/TICKETING.fa.md`.

خطاها JSON `{ok:false, error}` است؛ 401 توکن نامعتبر/باطل/منقضی، 403 مخزنِ
پروژهٔ دیگر، 404 منبعِ غایب در همین پروژه، 409 مخزن هنوز آماده نیست،
429 سقف نرخ، 503 داکر/گیتا در دسترس نیست.

## تضمین‌های امنیتی (ساختاری، نه اعتمادی)

1. **دانهٔ توکن:** توکن در دیتابیس فقط هش sha256 دارد؛ مالکش یک پروژه است.
   هیچ کوئری پل نمی‌تواند پروژهٔ دیگری را صدا بزند (IDOR-safe به‌ساختار).
2. **کشف کانتینر فقط با لیبل:** `parastoo.project=<id>` — نام سرویس ورودی فقط
   کلید در همین دانه است؛ نام هر کانتینر دیگری عملاً دیده نمی‌شود.
3. **بدون دسترسی هاست/داکر/زیرساخت:** عامل docker.sock، شل سرور، core،
   ترافیک، گیتا-ادمین و TLS ندارد؛ فقط مسیرهای پل.
4. **سقف‌ها:** exec (۱۲۰ث/۲۵۶KB)، لاگ (۲۰۰۰خط/۱۰۰KB)، push (۲۰۰MB)،
   سقف نرخ به‌ازای هر توکن و هر باکت (exec ۲۰/دقیقه، build ۱۰/ساعت، git ۳۰/ساعت).
5. **audit کامل:** هر فراخوانی در `DATA_DIR/dev/bridge-audit.jsonl` (پیشوند
   توکن + اقدام + جزئیات) — عامل فقط رکوردهای توکن خودش را می‌بیند؛ ادمین همه.
6. **ابطال فوری و انقضای اختیاری** (۱ تا ۳۶۵ روز) از صفحهٔ پروژه.
7. **نمایش یک‌بار:** مقدار کامل توکن فقط در پاسخ ساخت نمایش داده می‌شود؛
   بعدش فقط اثر انگشت (پیشوند ۱۲ کاراکتری).

## قواعد چرخهٔ توسعه–تست با پل (برای عامل)

- `pst push` همیشه HEADِ کامیت‌شده را می‌فرستد؛ کارِ نیمه‌کاره را کامیت کن یا
  stash کن (مثل هر پوش گیت). از v0.4.5 قبل از پوش، هم‌خوانی HEAD با main ریموت
  چک می‌شود — اجرای pst از پوشهٔ والدِ کلون (داخل مخزن گیت دیگر) با پیام روشن رد
  می‌شود، و کلونِ عقب با «اول pull».
- پوش = بیلد ایمیج‌ها؛ **استقرار همان کامیت برای پروژه‌ای که سایت منتشرشده دارد.**
  پروژهٔ تازه بدون سایت فقط ایمیج می‌گیرد — اجرای کانتینرها با «انتشار سایت»
  (دکمهٔ پنل یا POST /projects/<slug>/publish) است و به موجودی کیف پول
  (≥ یک ساعتِ کل سرویس‌ها) نیاز دارد. اولین سفر توسعه‌دهنده: init/clone ← کد ←
  push ← انتظار بیلد ← **انتشار سایت از پنل** ← بعد status/exec/restart با pst.
- تست = `pst exec -- <دستور>`؛ خروجی exit code واقعی برمی‌گردد.
- اگر سرویس گیر کرد: `pst logs` → عیب‌یابی → `pst restart`.
- `pst audit` گزارش پاسخ‌گویی عامل به مالک است — در پایان جلسه نشانش بده.

## مرزها و ریسک‌های باقی‌مانده (صادقانه)

- کانتینرِ سرویس عمومی به شبکهٔ `parastoo-apps` هم وصل است (برای ترافیک)؛ در
  آن شبکه هسته و ترافیک هم حضور دارند. دیوار ایزولگی اصلی، شبکهٔ خصوصی هر
  پروژه است؛ گام سخت‌گیرانهٔ بعدی، جداکردن شبکهٔ روترینگ ترافیک از شبکهٔ
  مدیریتی هسته (بیمهٔ دفاع در عمق) است — ایدهٔ ثبت‌شده برای نسخهٔ بعد.
- exec داخل کانتینر یعنی عامل با هر توانایی که کانتینر خود کاربر دارد —
  این دقیقاً هدف است (تست و عیب‌یابی)؛ مرزِ بیرونی همان ایزولگی کانتینر است.
- `pst` توکن را در `.parastoo.json` (سقف ۶۰۰) یا env نگه می‌دارد؛ پوش با URL
  توکار، توکن را برای لحظه‌ای در argv می‌گذارد — روی دستگاه تک‌کاربرهٔ عامل
  پذیرفتنی است؛ برای حساسیت‌های بیشتر، از `git credential` استفاده کن.
